## 🔴 C1 — Double-allocation de la couverture or (double-dépense inversée)

**`packages/api/src/services/consignment.service.ts:230-258`**

`auditValidate` place dans un même `db.batch` l'UPDATE gardé du lot et l'allocation du stock :

```sql
-- statement [0] : gardé
UPDATE gold_consignments SET status='AUDIT_VALIDATED', ... WHERE id = ? AND status = 'ARRIVED_DUBAI'
-- statement [2] : NON gardé
UPDATE gold_stock SET total_allocated = total_allocated + ? WHERE id = 'main'
```

En SQLite/D1, **un UPDATE qui ne matche aucune ligne n'est pas une erreur** : il ne fait pas échouer le batch.
Si une requête concurrente valide le lot entre le pré-contrôle (`getById`, ligne 224) et le batch, le statement `[0]`
touche 0 ligne — mais `[1]`, `[2]` et `[3]` sont commités quand même. Le code lit `changes === 0` **après** le commit
et renvoie `CONFLICT` : l'appelant croit que rien ne s'est passé, alors que la couverture tokenisable a déjà été
gonflée du poids raffiné.

**Reproduit** (`packages/api/test/integration/consignment-race.poc.test.ts`, fichier local non versionné) :

```
AssertionError: expected 910 to be 10
```

+900 g de couverture alloués sans or physique en face, pendant que l'API répond `CONFLICT`.

**Impact.** `reserveStock` autorise l'émission tant que `total_allocated - tokens_issued >= montant`. Gonfler
`total_allocated` permet donc d'émettre des tokens **non adossés à de l'or réel** — c'est exactement l'invariant
fondamental de la plateforme (`CHECK (tokens_issued <= total_allocated)`, `0001:198`) qui est contourné par le haut.
Le déclencheur demande un compte `consignments:approve` et une course, mais un retry client sur timeout suffit à
créer la fenêtre.

**Correctif recommandé.** Rendre la garde *fatale* pour le batch plutôt que consultative. Le plus robuste, une ligne
de migration :

```sql
CREATE UNIQUE INDEX idx_consignment_events_unique_transition
  ON consignment_events(consignment_id, to_status);
```

Chaque statut n'est atteignable qu'une fois (la machine à états est monotone), donc une seconde validation fait
échouer l'INSERT d'événement → le batch entier est annulé, allocation comprise. Le `catch` existant renvoie déjà
`CONFLICT`. Variante applicative : conditionner l'allocation au succès de la transition via
`WHERE ... AND EXISTS (SELECT 1 FROM gold_consignments WHERE id = ? AND status='AUDIT_VALIDATED' AND audited_by = ?)`.

## 🔴 C2 — Lecture arbitraire du bucket R2 via les photos de consignation

**`packages/api/src/routes/producer.ts:39,132-145` + `services/consignment.service.ts:103`**

Les clés R2 des photos sont fournies **par le client** et stockées telles quelles :

```ts
photos: z.array(z.string().max(256)).max(20).optional()   // aucune contrainte de forme
```

puis relues sans validation de préfixe :

```ts
const key = keys[Number(idx)];
const obj = await c.env.STORAGE.get(key);   // n'importe quelle clé du bucket
```

Un producteur authentifié soumet un lot avec `photos: ["kyc/<id-victime>/front_1699999999.jpg"]`, puis appelle
`GET /producer/consignments/<id>/photos/0` et récupère l'objet. Les documents KYC vivent dans **le même bucket**
(`users.ts:536`, `kyc/<userId>/<type>_<ts>.<ext>`). Le même défaut existe côté admin (`admin.ts:3065-3071`).

**Atténuation partielle** : les pièces KYC sont chiffrées AES-256-GCM *si* `ENCRYPTION_KEY` est défini — voir E1,
qui rend cette protection facultative. Restent lisibles en clair dans tous les cas : certificats, photos des autres
producteurs, et tout objet non chiffré du bucket.

**Correctif.** Ne jamais accepter de clé client. Soit l'upload renvoie un identifiant opaque résolu côté serveur,
soit on valide `key.startsWith(\`consignments/${userId}/\`)` **à la création et au streaming**.

## 🔴 C3 — Jetons interchangeables entre les trois portails (élévation de privilège)

**`packages/api/src/routes/admin.ts:102`, `state.ts:74`** — trouvé en auditant les profils, après la première passe.

Les trois surfaces d'authentification — client (`/auth/login`), back-office (`/admin/login`) et portail État
(`/state/login`) — signent leurs jetons avec **le même `JWT_SECRET`** et **la même charge utile**
(`sub`, `email`, `kycLevel`, `type`, `sid`). Rien n'y indique le portail émetteur. Or les deux middlewares
privilégiés identifiaient l'appelant sur le seul `payload.email` :

```ts
const adminUser = await c.env.DB
  .prepare('SELECT ... FROM admins WHERE email = ? AND active = 1')
  .bind(payload.email)   // ← d'où que vienne le jeton
```

Conséquence : **tout jeton d'accès valide dont l'e-mail correspond à une ligne active de `admins` ouvrait
`/admin/*`** — y compris un jeton émis par le login client ordinaire. Or `/admin/login` impose un TOTP
(`two_factor_enabled` vaut 1 par défaut) que le login client n'impose pas. Un administrateur disposant aussi
d'un compte client sur la même adresse contournait donc entièrement la double authentification du back-office,
et un jeton `STATE_OPERATOR` accédait au back-office là où son portail ne montre que des agrégats.

**Correctif.** Les jetons privilégiés portent désormais le portail émetteur (`portal: 'admin' | 'state'`),
que chaque middleware exige. La logique est isolée dans `lib/portal.ts`, avec les rôles répartis entre
`ADMIN_PORTAL_ROLES` et `STATE_PORTAL_ROLES` — `STATE_OPERATOR` étant délibérément exclu du back-office.
Un test vérifie que **tout rôle de `ROLE_DEFAULTS` appartient à exactement un portail**, pour que la panne
qui avait rendu `TRANSITAIRE` inassignable ne puisse pas se rejouer sur les frontières d'accès.

> **Effet au déploiement** : les jetons admin et État déjà émis n'ont pas le claim et seront refusés.
> Les administrateurs et opérateurs État devront se reconnecter une fois. Les clients ne sont pas affectés.
> Les portails admin et État n'ayant pas d'endpoint de refresh, aucune rotation n'est cassée.

## 🔴 C4 — Une base fraîche démarrait avec 10 kg d'or fictif

Trouvé en essayant simplement d'appliquer la migration du paiement producteur. **La chaîne de
migrations n'avait jamais été exécutée de bout en bout.** Elle cassait en `0011`, et cinq défauts
distincts se cachaient derrière :

| Migration | Défaut |
|---|---|
| `0002_seed_admins` | Seed déguisé en migration : `SUPER_ADMIN` + `STATE_OPERATOR` actifs, et **`gold_stock.total_allocated = 10000`** |
| `0011_seed_development` | `INSERT INTO system_config` — la table s'appelle `config`. **C'est ici que la chaîne s'arrêtait** |
| `0012_seed_staging` | `updated_by = 'staging-setup'` viole la FK vers `admins(id)` ; `INSERT OR REPLACE` sur `users` supprime des lignes référencées par `wallets` |
| `0014_performance_indexes` | Index sur `withdrawals(user_id, ...)` et `alerts(status, ...)` — **ces colonnes n'existent pas** |
| `0017` / `0018` | `DROP TABLE` sous clés étrangères actives (voir E2) |

**Le point critique est `0002`.** Toute base construite par la chaîne partait avec 10 000 g d'or
alloué — donc tokenisable et vendable — alors qu'aucun or physique n'existe en face. C'est
l'invariant fondateur `tokens_issued <= total_allocated` contourné dès l'installation, et par
défaut, pas par un cas limite. `0015` ne fait que relever cette valeur (`MAX`), jamais la remettre
à zéro. Ces mêmes fichiers plaçaient aussi en production des comptes `SUPER_ADMIN` dont l'en-tête
annonce « Password for all: Admin123! ».

Rien de tout cela ne s'est produit **uniquement parce que la chaîne cassait en `0011`**. Le bug
protégeait la production par accident : corriger `0011` seul aurait levé la protection.

**Correctif.** Les trois seeds sortent de `migrations/` vers `packages/api/seeds/` (voir son
README), les index de `0014` visent les vraies colonnes, et les scripts `db:*` pointent enfin sur
les bons noms de base (`tnc-trading-db-dev-v2` / `-staging` / `-production` ; `db:seed` déléguait à
un script inexistant). L'amorçage relève désormais des seules routes `/setup/*`, protégées par
`SETUP_SECRET`.

**Vérifié** : la chaîne `0001 → 0018` s'applique intégralement sur une base neuve, qui se termine
avec 0 admin, 0 utilisateur, 0 g alloué et 0 violation de clé étrangère.

## 🟠 E1 — Chiffrement des documents KYC en *fail-open*

**`packages/api/src/routes/users.ts:543-547`**

```ts
if (c.env.ENCRYPTION_KEY) {
  uploadData = await encryptionService.encrypt(arrayBuffer);
  isEncrypted = true;
}
```

Si le secret n'est pas injecté, les pièces d'identité partent en clair dans R2, **silencieusement**. L'audit
précédent a corrigé exactement ce motif pour `isProviderEnabled` (action #4, fail-closed) ; la même règle doit
s'appliquer ici : refuser l'upload plutôt que dégrader la protection sans le dire.

## 🟠 E2 — Migration 0017 : `DROP TABLE admins` avec 8 clés étrangères entrantes

**`packages/api/migrations/0017_gold_consignments.sql:31`**

La table `admins` est reconstruite (SQLite ne sait pas modifier un CHECK) via
`CREATE admins_new → INSERT SELECT → DROP admins → RENAME`. Or 8 colonnes la référencent :

`audit_logs.admin_id` (0001:242), `kyc_documents.reviewed_by` (0001:92), `withdrawals.approved_by` (0001:160),
`por_reports.verified_by` (0001:267), `system_config.updated_by` (0001:313), `admin_permissions.admin_id` (0009:7),
`integrations.updated_by` (0009:27), `blocked_ips.blocked_by` (0003:126).

Avec l'application des FK, `DROP TABLE` déclenche un `DELETE` implicite → violation de contrainte sur une base
peuplée, et la migration échoue **après** avoir créé `admins_new`. Les tests ne le voient pas : le helper `real-d1.ts`
désactive volontairement les FK (ligne 84-85).

**Correctif.** Encadrer par `PRAGMA defer_foreign_keys = ON` (supporté par D1) et **répéter la migration sur une copie
de la base de production** avant application. Les `id` étant préservés, le report des contraintes au commit suffit.

## 🟠 E3 — Type MIME non vérifié à l'upload

**`producer.ts:102-105`, `users.ts:507-517`** — `file.type` provient de l'en-tête multipart, donc du client. Aucune
vérification des *magic bytes*. La liste blanche (`jpeg/png/webp`) empêche le service de `text/html`, mais un objet
arbitraire peut être stocké puis re-servi avec un `Content-Type` d'image.

## 🟡 D1 — Chaîne de dépendances

`pnpm audit` remonte **140 advisories** (3 critiques, ~24 hautes distinctes). La lecture importante est
*où* elles se trouvent : le Worker déployé ne dépend que de `hono`, `jose`, `zod`, `argon2-browser` et
`@hono/zod-validator`. Tout le reste est outillage de build ou de test.

**Dans le runtime déployé** — deux advisories `hono@4.11.7`, **aucune des deux exploitable ici** :

| Advisory | Correctif | Exploitable ? |
|---|---|---|
| Accès arbitraire aux fichiers via `serveStatic` (`<4.12.4`, haute) | `>=4.12.4` | Non — `serveStatic` n'est pas importé (`index.ts` n'utilise que `cors`, `logger`, `secure-headers`, `timing`, `pretty-json`, `cookie`) |
| `memo()` retient la sortie SSR entre requêtes → fuite inter-utilisateurs (`<4.12.34`, modérée) | `>=4.12.34` | Non — pas de JSX/SSR côté API |

Monter `hono` reste la bonne hygiène (Dependabot a déjà des PR ouvertes), mais ce n'est pas un correctif urgent.

**Hors runtime** — les 3 critiques sont toutes dans l'outillage : `vitest <3.2.6` (lecture de fichier arbitraire
quand le serveur UI écoute — le mode UI n'est pas utilisé en CI), `shell-quote` et `tar` via la chaîne de build
`apps/mobile`. Les ~24 hautes suivent le même schéma : `vite`, `rollup`, `postcss`, `@babel/*`, `sharp`, `undici`,
`ws`, `lodash`, tous en dépendances de développement.

**Conclusion.** La surface d'attaque *déployée* venant des dépendances est aujourd'hui nulle. Le volume vient du
toolchain, et notamment de la chaîne Expo/React-Native. C'est cohérent avec la décision de l'audit précédent de ne
pas rendre `pnpm audit` bloquant en CI sans triage préalable — ce triage-ci confirme qu'un blocage brut noierait
les vrais signaux. La règle utile serait : **bloquant sur les dépendances de production uniquement**.
